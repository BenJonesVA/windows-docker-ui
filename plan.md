

## Evaluation (2026-07-28)

Status of the original 13 items, based on reading the current codebase:

1. **Firewall (VM↔host / VM↔VM)** — **Implemented (2026-07-28).** `docker/firewall.ts` applies host iptables rules per instance via a short-lived privileged helper container (`webui/firewall-helper/`, spawned through the existing Docker socket): blocks sandbox→host (`INPUT` drop on the instance's bridge — the gap that was actually open, confirmed empirically) and sandbox→RFC1918/link-local egress (`DOCKER-USER`, scoped to exclude same-bridge traffic so the webui↔sandbox viewer path is untouched). Wired into `template.ts` (apply on create, remove on teardown) and the reconciler (idempotent reapply every sweep so a host reboot self-heals). General internet stays open — required for the ISO fetch on first boot; DNS resolution confirmed unaffected. Remaining scope belongs to #16 (admin-configurable per-tier egress policy/allowlist) — what shipped here is a fixed defense-in-depth baseline, not a configurable policy.
2. **Network traffic monitoring (Remnux?)** — Not started. Blocked on a capture-point decision: passt gives no host-visible tap by default, so this needs a deliberate mechanism (e.g. switch a monitored tier to bridged/tap networking, or run capture from inside the guest), not just "point Remnux at the bridge."
3. **Wireshark integration** — Same blocker as #2. Depends on whatever capture point #2 lands on.
4. **Improve UI and add admin functions** — Superseded/absorbed by new item below (admin panel, resource tiers). Keep as a general UI-polish backlog item otherwise.
5. **Admin credential setup screen on deploy** — **Implemented (2026-07-28).** `GET /api/setup/status` reports `needsSetup: true` only when the `users` table is empty; `POST /api/setup` creates the first account with `role: 'admin'` and logs it in immediately, re-checking the user count at request time (not trusting the client's last `/status` read) so it can't be used to slip in a second "first admin" once setup is done. `App.tsx` shows a new `Setup` screen instead of `Login` while unauthenticated and `needsSetup` is true. Doesn't replace `db/seed.ts` (still useful for scripted/non-interactive deploys) — this is the interactive first-boot path. Verified against the live deploy: `needsSetup: false` (correct — the seeded admin already exists) and `POST /api/setup` correctly 409s once a user exists, which is the actual security property this route needs to hold. The empty-DB path (real `needsSetup: true` → submit → land in the app) wasn't exercised, since this host already has an admin seeded.
6. **Admin panel (users, resources, memory/cpu/disk settings)** — **Implemented (2026-07-28), user management + oversight only.** `role` enum and `requireAdmin` (previously unwired) now back real routes: `GET /api/admin/users` (list, with role/disabled state), `POST /api/admin/users/:id/disable`/`enable` (a disabled user's session is refused immediately — `resolveSession` already checks `disabledAt` on every request — and an admin can't disable their own account), and `GET /api/admin/instances` (every user's instances, read-only oversight — start/stop/delete/rename/egress still go through the owner-scoped routes in `api/instances.ts` unchanged, this isn't a parallel management surface). New "Admin" nav item, visible only to `role: 'admin'`. Explicitly NOT in scope here: resource-tier editing (RAM/CPU/disk bounds, idle/lifetime timeouts) — that's item #14's separate `resource_tiers` table, deliberately kept out so this panel didn't have to invent that schema decision to ship user management. Verified the new routes 401 without auth against the live deploy; the 403-for-non-admin branch (`requireAdmin`, pre-existing/unmodified) wasn't separately exercised — no non-admin test account exists on this host.
7. **Hover-to-preview screenshot of instance** — Not started, no existing capture code. Needs a mechanism: QEMU screendump via the monitor socket, or a periodic screenshot pulled through the noVNC/websockify viewer. Worth a small spike to see which dockur/windows exposes.
8. **Client↔sandbox clipboard copy/paste** — **Already done.** noVNC clipboard passthrough is enabled on the viewer iframe (`allow="clipboard-read; clipboard-write"`, `InstanceDetail.tsx:138`) and called out in the UI (`InstanceDetail.tsx:246`). No further work unless testing surfaces a gap.
9. **Browser file upload into the OS** — **Flagged as a decision, not a task.** The UI currently states, deliberately, "File transfer and RDP are not exposed — the viewer is the only path in." Enabling upload reverses that stated security posture. Two real options: (a) keep the current invariant and close this item, or (b) add upload into an isolated scratch volume/share *only* for a clearly-labeled "sandbox" tier, with the exposed-attack-surface tradeoff spelled out. Needs an explicit call before any implementation.
10. **Show/remove downloaded OS images in UI** — Narrower than worded: dockur/windows pulls the Windows ISO from Microsoft itself at first boot; this project has no hook into that. What's actually manageable and worth exposing: the pinned base Docker image, and per-instance Docker volumes (the real disk consumer). Rescope to "manage sandbox volumes/images," not "manage Windows ISOs."
11. **Evaluate anything missing** — This evaluation pass + the new items below.
12. **Resource monitor (CPU/mem/disk) in UI** — **Implemented (2026-07-28), CPU/mem only.** `GET /api/instances/:id/stats` uses `docker/template.ts`'s new `getInstanceStats`, wrapping dockerode's `stats({ stream: false })` (which internally samples twice ~1s apart even in non-streaming mode, which is what makes the standard cpu/system-delta formula meaningful rather than a divide-by-zero). Displayed as a live-updating "Live usage" panel on InstanceDetail (CPU% and memory usage/limit bars), polling every 3s while running. Verified against a real running sandbox container on the live host — 4.57% CPU, ~2.99GB/4GB memory, matching the container's configured RAM. Disk usage deliberately excluded: the guest's actual disk lives in a bind-mounted volume, not the container's own writable layer, so `docker inspect --size` doesn't reflect it — real volume usage would need a `du`-via-helper-container mechanism (same pattern as `firewall.ts`), a separate follow-up.
13. **Record process executions / network traffic / other metrics** — Not started, and the biggest lift of the list. No telemetry pipeline exists at all (only stdout/stderr log tailing today). Requires either an in-guest agent (process list) or a host-side capture mechanism (network — see #2/#3), plus a place to store and query time-series/event data. Should follow, not precede, the egress/capture decisions in #1-#3.

**Naming note (resolved 2026-07-28)**: the code comments that referenced a "task #8" (unrelated to this plan.md's own item 8, clipboard) now point at the correct item numbers — `reconciler/index.ts` and `docker/validators.ts` at #14 (resource tiers), `api/auth.ts`/`db/seed.ts`/`api/setup.ts` at #6's remaining scope (admin-invite registration).

## New items (additions, 2026-07-28)

14. **Per-tier resource limits, admin-configurable** — **Implemented (2026-07-28), single-tier scope.** The hardcoded constants in `reconciler/index.ts` (idle/lifetime) and `docker/validators.ts` (RAM/CPU/disk bounds) are gone, replaced by a `resource_tiers` table (`db/resourceTiers.ts`'s `getActiveTier()` lazily seeds the one row with the exact same values these constants used to hold, so behavior is unchanged until an admin edits it — confirmed against the live deploy). `docker/validators.ts`'s `createInstanceSchema` became `buildCreateInstanceSchema(tier)`, built fresh per request in `api/instances.ts` (both the create route and `/meta`) so a tier edit takes effect immediately. Admin edits it via `PUT /api/admin/resource-tier` and a form on the new Admin page. The per-instance max-uptime override: `sandbox_instances.max_uptime_override_seconds` (nullable — null defers to the tier), set via `POST /api/admin/instances/:id/max-uptime`, read by `reapIdleAndExpired` ahead of the tier default. Deliberately still ONE tier, not a multi-tier system — letting a user pick from several tiers (or restricting users to specific tiers) is a real UX/access-control design decision (that's the rest of this item's original scope plus #15's territory) that shouldn't be invented without the user's input; what shipped here is the "admin-configurable" half only.

**Follow-up (2026-07-28)**: added a third max-uptime level per user request — `users.max_uptime_override_seconds` (nullable), set via `POST /api/admin/users/:id/max-uptime`. Precedence in `reapIdleAndExpired`: instance override > user override > tier's global default. Also fixed a real Admin-page layout bug (screenshot-reported): the Users and All-instances panels were misusing `.vm-spec-k`/`.vm-spec-row` (a fixed-88px-width, dimmed-text style meant for short static labels like "Image"/"vCPU") to hold wide dynamic content — emails, instance names — causing overlapping/garbled text and washed-out color. Replaced with new `.vm-admin-row`/`-main`/`-side` classes that flex/wrap properly.
15. **Per-user quotas** — **Implemented (2026-07-28).** Added to the same `resource_tiers` row #14 introduced (one tier today, so this is a global-not-yet-per-user quota in practice — same scope caveat as #14): `maxConcurrentInstances`, `maxAggregateRamMb`, `maxAggregateDiskGb`. Enforced in `api/instances.ts`'s `checkUserQuota`, called from the create route before insert — counts/sums the requesting user's own live (non-deleted) instances against the tier and 409s with a specific message if creating this instance would exceed any of the three. New columns got SQL-level defaults (5 concurrent / 40960 MB / 640 GB — generous enough that 5 instances at the per-instance max still fit) precisely so the migration backfills the already-seeded tier row without breaking anything currently running; confirmed against the live deploy — the existing user's 3 live instances (12,288 MB RAM, 96 GB disk total) sit comfortably under the new ceiling. Admin edits these via the same Resource tier form as #14.
16. **Egress control for sandbox networking** — **Implemented (2026-07-28), per-instance scope.** The real gap behind item #1 once VM↔VM/VM↔host isolation was already in place. Shipped as a per-instance policy (`open` / `blocked` / `allowlist` + CIDR list) rather than a per-tier one — #14's `resource_tiers` table doesn't exist yet, so a per-tier default is future work layered on top of this, not blocking it. Implementation note: the flat `-I DOCKER-USER 1` insertion #1/#23 used can't safely express an ordered allow-then-deny policy (whichever rule was last reapplied would land on top across reconciler sweeps), so `docker/firewall.ts` now gives each instance its own iptables chain (`SBX-<iface>`), jumped to once from `DOCKER-USER`, flushed and rebuilt in a fixed, deterministic order every apply: baseline RFC1918/link-local drops, then (allowlist mode) an unconditional DNS-port-53 accept + the admin-entered CIDRs as ACCEPT, then a trailing DROP. `sandbox_instances.egress_mode`/`egress_allowlist` are the source of truth; the reconciler's per-sweep `ensureFirewallRules` now maps `sbx-*-net` back to its instance row and rebuilds that instance's chain to match, same self-healing pattern as the baseline. `POST /api/instances/:id/egress` + a mode-select/CIDR-textarea control in InstanceDetail's Access panel. Not verified at runtime against a live allowlist (no /dev/kvm in this environment) — verify empirically before relying on it in production.
17. **Decision needed: sandbox network/capture tier**. Items #2, #3, #13's network half, and #16 all depend on the same underlying choice: passt/usermode networking (current default) has no host-visible tap, so traffic monitoring and Wireshark integration require either switching a "monitored" tier to bridged/tap networking, or capturing from inside the guest. Resolve this once, then implement #2/#3/#16 against it — don't solve it three times.
18. **File upload — decision, not a task**: see evaluation item #9 above. Needs an explicit choice between preserving the current "viewer is the only path in" invariant, or adding scoped upload for a labeled sandbox tier with the tradeoff acknowledged.
19. **Volume/image housekeeping** — **Implemented (2026-07-28), scoped narrowly.** Rescope of item #10 confirmed: what's manageable is per-instance Docker volumes and the pinned base image, not Windows ISOs (this project never controls those). Deliberately scoped to what doesn't require inventing admin infrastructure that doesn't exist yet (#6): `DELETE /api/instances/:id` with `retain_disk=true` left a volume behind with zero visibility or way to reclaim it — the soft-deleted instance row (`deletedAt` set) just sat there unseen. `GET /api/instances/retained-volumes` now surfaces the current user's own soft-deleted rows whose volume still actually exists (checked live against Docker, so a row already cleaned up doesn't linger forever), and `DELETE /api/instances/:id/volume` permanently removes it. Surfaced in a collapsible "Retained disks" panel on the Dashboard. The pinned base image (`docker/template.ts`'s `IMAGE_REF`, now exported) is exposed read-only via `/api/instances/meta` and shown at the bottom of the Dashboard. Not in scope here: a cross-user "all volumes on this host" view — that's real admin-panel territory (#6), not per-user housekeeping. Verified the new routes are registered and auth-gated (401s) against the live deployed container; not exercised through an authenticated session.
20. **Rename sandbox sessions** — **Implemented (2026-07-28).** `PATCH /api/instances/:id` accepts `{ name }`, validated by a shared `instanceNameSchema` (`docker/validators.ts`) now used by both create and rename so the two paths can't drift. Renaming only ever touches the DB row — `containerName`/`volumeName` (the real Docker resource names) are fixed at create time and untouched. Inline-edit control shipped on both InstanceDetail (click the title) and the Dashboard row (pencil icon). Verified the route is registered and auth-gated (401 on an unauthenticated request against the live deployed container); the actual rename flow through a real login session was not exercised — do that once before relying on it.
21. **Linux sandbox OS support**: the platform itself is already OS-agnostic — per-instance network/firewall, resource limits, reconciler, volume-backed disk, and the viewer proxy have nothing Windows-specific in them. The Windows-specific surface is narrow: the pinned `dockurr/windows` image (`docker/template.ts:9-11`) and the `VERSION`-driven enum/disk-minimum logic in `docker/validators.ts`. Likely shape: a second QEMU-in-Docker image for Linux distros/cloud images (same maintainer line as `dockurr/windows` reportedly has a sibling for this — verify the exact image and its env-var contract before committing), plus an OS-type dimension in the schema so Linux gets its own version enum and disk minimums rather than reusing Windows'. Needs a design pass before implementation, not just a template swap.
22. **Snapshot and clone support**: each instance's disk is a single Docker volume (`Binds: [\`${volumeName}:/storage\`]`, `docker/template.ts`), so the mechanism depends on what's actually on disk — a QEMU-level snapshot (qcow2 internal snapshot / monitor-socket `savevm`, if dockur/windows' `DISK_OPTIONS`/`STORAGE` format supports it) would be fast and let a running instance roll back in place; a Docker-volume-copy clone (new volume + `docker cp`/tar of the source volume's contents) is format-agnostic but only works stopped and is as slow as the disk is large. Needs a spike to confirm the actual disk format/QEMU flags in use before picking a mechanism — don't assume qcow2 without checking.
23. **Per-instance network ingress/egress toggle in the web UI** — **Implemented (2026-07-28).** "ingress" is already zero today by design — no published ports, no inbound path except the webui's own proxy (see #18's "viewer is the only path in" invariant) — so there's nothing to toggle there; this shipped as an **egress on/off switch**. `sandbox_instances.egress_blocked` (migration `0002_workable_exodus.sql`) is the source of truth; `docker/firewall.ts`'s `ensureInstanceFirewall(networkId, { blockEgress })` ensures-or-removes a deny-all `DOCKER-USER` rule (same-bridge-scoped like the baseline RFC1918 rules, so the webui↔sandbox viewer path survives a block) based on the flag, and `removeInstanceFirewall` now unconditionally removes that rule too so orphan-network/teardown cleanup can't leak it. `POST /api/instances/:id/egress` persists the flag and applies it immediately if the instance's network already exists (otherwise the reconciler's per-sweep `ensureFirewallRules`, which now maps each `sbx-*-net` back to its instance row, converges it within one sweep — same self-healing pattern as the baseline rules). UI control lives in InstanceDetail's Access panel next to the existing "viewer is the only path in" copy. Distinct from #16 (admin-set default policy per tier) — this is a live, per-instance override a user triggers themselves.
