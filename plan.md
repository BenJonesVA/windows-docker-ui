Status of the original 13 items, based on reading the current codebase:

1. **Firewall (VM↔host / VM↔VM)** — **Implemented (2026-07-28).** `docker/firewall.ts` applies host iptables rules per instance via a short-lived privileged helper container (`webui/firewall-helper/`, spawned through the existing Docker socket): blocks sandbox→host (`INPUT` drop on the instance's bridge — the gap that was actually open, confirmed empirically) and sandbox→RFC1918/link-local egress (`DOCKER-USER`, scoped to exclude same-bridge traffic so the webui↔sandbox viewer path is untouched). Wired into `template.ts` (apply on create, remove on teardown) and the reconciler (idempotent reapply every sweep so a host reboot self-heals). General internet stays open — required for the ISO fetch on first boot; DNS resolution confirmed unaffected. Remaining scope belongs to #16 (admin-configurable per-tier egress policy/allowlist) — what shipped here is a fixed defense-in-depth baseline, not a configurable policy.
2. **Network traffic monitoring (Remnux?)** — **Implemented (2026-07-29).** Resolved via #17's decision: `passt` (the usermode networking backend already in production, `NETWORK=user`) has its own `--pcap FILE` flag ("Log tap-facing traffic to pcap file", confirmed via `passt --help` in the pulled `dockurr/windows` image) — zero networking-architecture change needed. `docker/template.ts`'s `buildEnv` now sets `PASST_OPTS=--pcap ${NETWORK_CAPTURE_PATH}`, writing to the same reserved `telemetry/` subfolder `#13`'s process collector uses (`docker/networkCapture.ts`'s `NETWORK_CAPTURE_PATH`). A new `ensureTelemetryDir` (`docker/telemetry.ts`) runs before container creation — unlike the process collector, which tolerates the folder not existing yet, `passt` opens its `--pcap` path once at container start, before Windows has even booted, so the directory must exist upfront. Not a Remnux/IDS integration — this is capture-to-file only, no live inline inspection (see #25's "wrong layer" framing: that needs a real inline traffic-inspection engine, which is out of scope). "Monitoring" here means "a downloadable capture exists," not a live dashboard.
3. **Wireshark integration** — **Implemented (2026-07-29), narrower than a live remote-capture integration.** Resolved as "download the capture, open it in your own Wireshark" — `GET /api/instances/:id/network-capture` (size/mtime, 404 if nothing captured yet) and `GET /api/instances/:id/network-capture/download` (owner-scoped, not gated on running, same posture as the shared-files routes), surfaced as a new "Network capture" panel on `InstanceDetail.tsx`. Deliberately NOT built: a live/remote Wireshark integration (rpcap/extcap-style) — that would need a new inbound network path reachable from the analyst's own Wireshark client, the same class of decision `#18` flagged for destination NAT, not something to build without an explicit ask. **User-suggested follow-up, not implemented this pass**: [QXIP/webshark](https://github.com/QXIP/webshark) (sharkd-based, AGPL-3.0, its own Docker service exposing a web UI on port 8085 against a `/captures` volume) would give in-browser viewing without a local Wireshark install — the clean integration is proxying its UI through the existing authenticated app (same pattern as the noVNC viewer), copying each instance's capture into its `/captures` volume on demand rather than exposing its port directly. Real separate work (new service, new proxy route, an AGPL license check worth doing deliberately rather than assuming) — scoped as a distinct follow-up, not folded into this pass.
    - **Real risk, not solved**: no pcap rotation. `passt` has no built-in log rotation, and externally truncating a file out from under its still-open write descriptor doesn't reset that descriptor's offset — the next write would land at the old offset, leaving a zeroed gap followed by orphaned record bytes with no valid pcap global header at the start. `docker/networkCapture.ts` deliberately never mutates the live file — only stats/reads it. Growth is bounded only by the instance's own idle-timeout/max-lifetime reaping, not by any cap (matches `#9`'s/`#15`'s "no per-tier knob yet" scoping) — a long-running session can produce a large capture file.
    - **A stale assumption corrected along the way**: `docker/template.ts` granted `/dev/net/tun` on the belief that without it, dockur "silently falls back to passt." Investigated by reading the real (unvendored) `windows/src/network.sh` from the pulled `dockurr/windows` image: `/dev/net/tun` is only ever touched by `configureNAT()`, which only runs when `isNAT()` matches — and `isNAT()` explicitly excludes `"user"` (this app's fixed `NETWORK=` value). Removed the device grant entirely (grepped every script in the image to confirm `network.sh` is the only consumer) — passt itself needs no tun/tap device, operating entirely over a unix socket. **Not verified against a live boot with the device actually removed** (no `/dev/kvm` in this environment) — verify if guest networking ever regresses.
    - **Verified empirically**: the Docker-side mechanics (`getNetworkCaptureInfo`'s stat parsing, `downloadNetworkCapture`'s byte-accurate read, missing-file → `null`) were run against a real Docker volume and the real `sandbox-firewall-helper` helper image — a synthetic 500,000-byte file round-tripped exactly, and a missing file correctly produced no result. **Not verified**: `passt` actually writing to this path against a real guest boot (no `/dev/kvm` here), and whether privilege-drop (`passt`'s own `--runas nobody`) affects its ability to keep the already-opened `--pcap` fd — daemons conventionally open log files before dropping privileges, which is almost certainly why this is fine, but "almost certainly" isn't "verified."
    - **Existing instances need recreation**: same situation as every other `/oem`/`/shared`-dependent feature (`#9`, `#13`) — `PASST_OPTS` is set at container-create time only.

7. **Hover-to-preview screenshot of instance** — **Implemented (2026-07-28).** Mechanism: dockur/windows' base image (`qemux/qemu`, not vendored in `windows/`) always starts QEMU with an HMP monitor on a unix socket at `$QEMU_DIR/monitor.sock` (`/run/shm` by default — confirmed by pulling `dockurr/windows` and reading its `/run/config.sh` + `/run/reset.sh` directly, since this isn't documented in `windows/docs`). `docker/template.ts`'s `captureInstanceScreenshot` runs two `docker exec`s into the instance's own container (no helper container needed, unlike `firewall.ts`'s pattern): one sends HMP's `screendump` command over the monitor socket via the image's own `openbsd-nc` and polls the resulting PPM file for two consecutive equal size reads (not just non-empty — a full 1920x1080 dump is several MB and a naive "-s file" check races a partial write); the other runs a pure-stdlib `python3 -c` (zlib only — the image ships no PIL/ImageMagick/netpbm) that re-encodes the PPM to PNG, with a length check against the declared width×height so a still-truncated read fails loudly (nonzero exit / no PNG magic) rather than emitting a structurally corrupt image. The PPM is deleted from tmpfs after conversion (best-effort). `GET /api/instances/:id/screenshot` (409 if not running, 502 on capture failure — same shape as `/stats`) serves the PNG directly; Dashboard.tsx shows it in a floating preview on a 350ms hover-intent delay over an instance's name (only for `running && phase === 'ready'` — nothing to capture pre-boot), refreshing every 4s while hovered. **Verified empirically without a live QEMU**: pulled the real `dockurr/windows` image and ran the exact trigger/convert commands against (a) a synthetic 1920x1080 PPM directly, and (b) a stub `AF_UNIX` monitor-socket listener that writes a real 6MB PPM in slow 300KB chunks (simulating an in-progress screendump) while driving the *actual* Node/dockerode `exec`+`demuxStream` code path from `template.ts` against a live container — the stability-poll correctly waited out the slow write, and the resulting PNG had valid magic bytes and correct dimensions end-to-end. Not verified: capture against a real booted Windows guest's actual QEMU monitor (this dev environment has no `/dev/kvm`-capable engine reachable from here) — the stub proves the mechanism and the race-condition fix, not real screendump content or its true write-latency profile.
8. **Client↔sandbox clipboard copy/paste** — **Corrected and implemented (2026-07-28).** The earlier "Already done" entry here was wrong: `allow="clipboard-read; clipboard-write"` on the iframe grants a browser permission, but does nothing by itself, and dockur/windows' own `windows/readme.md` says outright the web viewer "does not support ... clipboard sharing." Confirmed by pulling the image and reading `/usr/share/novnc/app/ui.js` directly: real noVNC (not KasmVNC), whose only clipboard feature is a manual panel (`clipboardSend`/`clipboardReceive` — open a sidebar textarea, paste text in to send it to the guest, guest-copied text lands in the same textarea for you to copy out yourself). No automatic OS-clipboard sync existed. Built real two-way sync instead: `webui/web/public/clipboard-sync.js` (new static asset, served at `/clipboard-sync.js`) dynamically imports the SAME `UI` module singleton the page's own inline script uses (`import(location.pathname.replace(/[^/]*$/, '') + 'app/ui.js')` — resolves to the identical absolute URL as vnc.html's own `import UI from "./app/ui.js"`, so the module cache hands back the same object, confirmed by reading vnc.html directly rather than assumed), then wires `UI.rfb`'s `clipboard` event to `navigator.clipboard.writeText` (guest copy → browser clipboard) and a `window focus` handler to `rfb.clipboardPasteFrom(navigator.clipboard.readText())` (browser copy → guest). `webui/src/proxy/viewer.ts`'s http-proxy now sets `replyOptions.onResponse`, which hands this app the raw upstream response for every proxied request (confirmed by reading `@fastify/reply-from`'s source: providing `onResponse` replaces its default `reply.send(res.stream)` entirely, so every non-HTML asset must still take that exact fallback path) — only `text/html` responses are buffered and get the script tag injected before `</body>`, with `Content-Length` recomputed against the modified byte length (the pre-injection header is already copied onto the reply by the time `onResponse` fires — leaving it stale would truncate the response in the browser). Verified the exact injection logic against the real `vnc.html` pulled from the image (correct byte delta, single injection point, valid surrounding context). Not verified: `navigator.clipboard.readText()` on window focus is well-known to be browser/permission-state dependent without a live user gesture — this can silently no-op on some browsers, and the real end-to-end behavior (both directions, in an actual browser, against a live QEMU monitor) has not been exercised — no `/dev/kvm` in this dev environment.
9. **Browser file upload into the OS** — **Implemented (2026-07-28).** Resolved the decision as scoped upload/download via dockur/windows' own built-in shared-folder feature, not a host filesystem path: `docker/template.ts` now sets `SAMBA=Y` (previously `N`) and binds a new per-instance volume (`sharedVolumeNameFor`, `sbx-<id>-shared`) at `/shared` — surfaced in the guest as a desktop shortcut + drive `Z:`, same lifecycle as the main disk volume (removed together on permanent delete, kept together on "retain disk"). `docker/files.ts` reads/writes that volume through a short-lived helper container (reuses `sandbox-firewall-helper:latest` — already a required deploy-time build for `firewall.ts`, so this added zero new deploy steps — with its `iptables` entrypoint overridden to `sleep` since `docker exec` needs a running container, unlike the archive-style approach originally considered) via the same exec-based approach `docker/template.ts`'s screenshot feature (#7) established, extracted into a shared `docker/exec.ts`. Filenames reach the shell as a positional arg (`sh -c '...' sh "$filename"`), never interpolated into script text, which rules out shell injection but NOT path traversal (`../etc/passwd` through a quoted arg still escapes `/shared` at the OS level, confirmed empirically) — `docker/validators.ts`'s new `sharedFileNameSchema` rejects `/`, `\`, and `..` before any of this runs. Fixed-cap limits (200MB/file, 2GB total per instance's shared folder) since there's no per-tier knob for this yet (#14's `resource_tiers` table doesn't cover it). New routes in `api/files.ts` (list/upload via `@fastify/multipart`/download/delete), all owner-scoped and deliberately NOT gated on the instance running — the volume exists independently of the container. UI: a new "Shared files" panel on `InstanceDetail.tsx`. **Found and fixed a real bug while building this**: `exec.inspect()` read immediately after a hijacked exec stream's `'end'` event can report a stale `Running: true`/null `ExitCode` for an exec that already finished successfully (confirmed empirically — a write-then-read pair intermittently saw this on a write that had, in fact, already persisted correctly) — `docker/exec.ts` now polls `inspect()` until `Running: false` before trusting `ExitCode`, a fix that also applies retroactively to #7's screenshot capture. Also found empirically: attaching stdin to an exec that has nothing to send and immediately `.end()`-ing it is unreliable (intermittently truncates the read to 0 bytes) where never attaching stdin at all is 100% reliable — `docker/exec.ts` only attaches stdin when there's real input to write. **Verified end-to-end**: ran the actual compiled module against a real Docker volume + helper container — list/upload/download/delete all round-tripped correctly, including a filename with spaces, parentheses, and a unicode em-dash, and a traversal/not-found case correctly threw rather than silently succeeding. Not verified: the real HTTP multipart route (`api/files.ts`) end-to-end through a browser, and the feature against an actual running Windows guest (no `/dev/kvm` here) — only the underlying `docker/files.ts` module and its exec mechanics were exercised directly. **Existing instances need recreation**: the `/shared` bind and `SAMBA=Y` are set at container-create time only (same situation as the earlier `/dev/net/tun` networking fix) — an instance created before this change has no `/shared` mount at all. `docker/files.ts`'s helper container would still mount `sbx-<id>-shared` (Docker silently auto-creates a missing named volume rather than erroring), so listing/upload/delete against an old instance would all report success while nothing ever reaches that instance's actual guest. New instances get this automatically; existing ones don't until recreated.

16. **Egress control for sandbox networking** — **Implemented (2026-07-28), per-instance scope.** The real gap behind item #1 once VM↔VM/VM↔host isolation was already in place. Shipped as a per-instance policy (`open` / `blocked` / `allowlist` + CIDR list) rather than a per-tier one — #14's `resource_tiers` table doesn't exist yet, so a per-tier default is future work layered on top of this, not blocking it. Implementation note: the flat `-I DOCKER-USER 1` insertion #1/#23 used can't safely express an ordered allow-then-deny policy (whichever rule was last reapplied would land on top across reconciler sweeps), so `docker/firewall.ts` now gives each instance its own iptables chain (`SBX-<iface>`), jumped to once from `DOCKER-USER`, flushed and rebuilt in a fixed, deterministic order every apply: baseline RFC1918/link-local drops, then (allowlist mode) an unconditional DNS-port-53 accept + the admin-entered CIDRs as ACCEPT, then a trailing DROP. `sandbox_instances.egress_mode`/`egress_allowlist` are the source of truth; the reconciler's per-sweep `ensureFirewallRules` now maps `sbx-*-net` back to its instance row and rebuilds that instance's chain to match, same self-healing pattern as the baseline. `POST /api/instances/:id/egress` + a mode-select/CIDR-textarea control in InstanceDetail's Access panel. 17. **Decision needed: sandbox network/capture tier** — **Resolved (2026-07-29): `passt`'s own `--pcap` flag.** Investigated by pulling the real `dockurr/windows` base image and reading its (unvendored) `network.sh` directly rather than trusting `windows/docs`/readme. Found the original framing was slightly wrong: switching to `NETWORK=nat`/tap mode would NOT give host-bridge-visible guest traffic either — `configureNAT` still NATs the guest out through the container's single IP before anything reaches the Docker bridge, same externally-opaque result as today's `passt`. 26. **Applied the "directly buildable" tier of #25** — **Implemented (2026-07-28), not verified at runtime.** Stateful packet inspection, anti-spoofing, a connection-rate safeguard, and policy dry-run detection, all layered onto the existing per-instance chain (`docker/firewall.ts`) rather than a parallel mechanism. Deliberately NOT done here: IPv6 (still gated on a bridge ever going dual-stack — hasn't happened), bandwidth shaping/QoS/`tc` (shaping direction on a bridge device — host-egress vs. guest-egress — can't be confirmed without a live host to test against; got this wrong in reasoning once already this session before catching it), and destination/1:1 NAT (still the #18-style decision — reverses the "viewer is the only path in" invariant, not implemented).
    - **Stateful fast-path**: `populateChain` now appends `-m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT` as the very first rule in every instance's chain, for every egress mode. Return/related traffic for an already-permitted connection now skips re-evaluation against the rest of the chain on every packet — this doesn't change what's reachable (a packet only reaches this state because its connection's initial packet already passed every check once), just how much re-runs per packet.
    - **Anti-spoofing (rp_filter)**: `ensureRpFilter` sets strict reverse-path filtering (`net.ipv4.conf.<bridge-iface>.rp_filter=1`) on each instance's own bridge interface. Runs via a brand-new, SEPARATE privileged helper image (`webui/net-helper/Dockerfile`, `ENTRYPOINT ["sysctl"]`) rather than widening `firewall-helper`'s own `ENTRYPOINT ["iptables"]` contract — doing that would've been a breaking change for any host that hasn't rebuilt that image (its Cmd-is-iptables-args shape would silently misparse). The new image needs its own one-time build step (`docker build -t sandbox-net-helper:latest ./webui/net-helper`, documented in `compose.yml` as step 4b) — **skipping it is safe**: `ensureRpFilter` fails silently (try/catch, no throw, no logger dependency in this module) if the image is missing, so a host that never builds it just doesn't get this one hardening feature; nothing else regresses. Also best-effort for a structural reason: the bridge interface may not exist yet the instant `ensureInstanceFirewall` first runs (right after network creation, before a container attaches), so an initial failure is expected, not exceptional — the reconciler's per-sweep reapply retries until it succeeds. Deliberately does NOT touch the host-wide `net.ipv4.conf.all.rp_filter` (Linux takes the max of that and the per-interface value) — a bigger blast-radius change than a per-instance feature should make unilaterally, so this is only fully effective if the host's own default is already ≥1.
    - **New-connection rate limiting**: reframed from the requested "SYN flood protection," which doesn't fit this app's actual topology — there's no inbound path to protect at all (plan item #23: ingress is already zero by design) — into defense-in-depth against this sandbox being used as a flood/scan SOURCE. Each instance gets a second, dedicated sub-chain (`SBX-<iface>-SYN`, `ensureSynFloodChain`) holding exactly two rules in a fixed order — `-m limit --limit 15/s --limit-burst 45 -j RETURN` then an unconditional `-j DROP` — jumped to from the main chain for `-p tcp --syn` traffic only, appended as part of every `populateChain` rebuild. Two correctness properties this depends on, both reasoned through carefully since neither could be tested against a live host: (1) the sub-chain must NEVER be flushed like the main chain is every sweep, or its `-m limit` token-bucket state resets every 60s and the limit becomes meaningless — a new `ensureRuleAppended` helper (check-then-`-A`/append, not check-then-`-I`/insert-at-top like the existing `ensureRule`) is what makes calling `ensureSynFloodChain` idempotently every sweep safe without ever touching its two rules again once they exist; (2) `RETURN` inside a JUMPED-TO sub-chain returns control to the chain that jumped into it (here, the instance's own main chain, right after the jump rule) — using `RETURN` directly in the main chain instead (the naive version of this feature) would have returned all the way out to `DOCKER-USER`, skipping every baseline/policy rule that comes after and silently granting general internet access to any in-budget SYN regardless of egress mode. **This is a real behavior change for every existing instance, not just profile users** — a legitimately connection-heavy workload (e.g. a package manager opening many parallel downloads) could hit the 15/s ceiling; the numbers aren't user-configurable today, and if they're ever tuned, note that `ensureRuleAppended`'s `-C` check compares the full rule spec including the limit numbers, so changing the constant appends a second, newer rule below the stale one rather than replacing it. Sub-chain teardown (`removeInstanceFirewall`) is ordered strictly after the main chain's own removal (which drops the only rule ever referencing the sub-chain, since iptables refuses to delete a still-referenced chain) and its own failure is swallowed rather than thrown, so a rare `-X` failure can't block the network-teardown work every caller still has left to do.
    - **Policy dry-run / rule-conflict detection**: purely client-side, in `web/src/lib/firewallAnalysis.ts` — flags (a) a rule whose destination CIDR falls entirely inside the always-on `BLOCKED_EGRESS_CIDRS` baseline (can never match, regardless of action) and (b) a rule shadowed by an earlier, broader rule in the same profile (same CIDR containment check plus a protocol/port-range covers check). Surfaced as an amber outline + "⚠" label prefix on the shadowed rule's node in `FirewallGraphEditor`, a summary banner listing every warning atop `FirewallProfileEditor`, and the specific message inline when a flagged rule is selected. Advisory only — `docker/firewall.ts` compiles and enforces whatever was saved regardless of what this flags; nothing server-side validates against it.
    - **Not verified at runtime, same posture as #16/#24**: none of the conntrack rule, the SYN sub-chain's RETURN semantics, the sysctl call, or rp_filter's actual effectiveness (which depends on the host's own `net.ipv4.conf.all.rp_filter`) have executed against a live Docker host — no socket/KVM in this environment, same limitation every prior firewall item shipped under. `tsc`/`vite build` passing confirms the types line up, not that any of this behaves as designed. Verify all of it — especially that a legitimate multi-connection workload doesn't get throttled, and that the RETURN/jump ordering actually preserves policy for in-budget SYNs — before relying on this in production.
