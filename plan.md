General internet stays open — required for the ISO fetch on first boot; DNS resolution confirmed unaffected. 5. **Admin credential setup screen on deploy** — **Implemented (2026-07-28).** `GET /api/setup/status` reports `needsSetup: true` only when the `users` table is empty; `POST /api/setup` creates the first account with `role: 'admin'` and logs it in immediately, re-checking the user count at request time (not trusting the client's last `/status` read) so it can't be used to slip in a second "first admin" once setup is done. `App.tsx` shows a new `Setup` screen instead of `Login` while unauthenticated and `needsSetup` is true. 6. **Admin panel (users, resources, memory/cpu/disk settings)** — **Implemented (2026-07-28), user management + oversight only.** `role` enum and `requireAdmin` (previously unwired) now back real routes: `GET /api/admin/users` (list, with role/disabled state), `POST /api/admin/users/:id/disable`/`enable` (a disabled user's session is refused immediately — `resolveSession` already checks `disabledAt` on every request — and an admin can't disable their own account), and `GET /api/admin/instances` (every user's instances, read-only oversight — start/stop/delete/rename/egress still go through the owner-scoped routes in `api/instances.ts` unchanged, this isn't a parallel management surface). New "Admin" nav item, visible only to `role: 'admin'`. Explicitly NOT in scope here: resource-tier editing (RAM/CPU/disk bounds, idle/lifetime timeouts) — that's item #14's separate `resource_tiers` table, deliberately kept out so this panel didn't have to invent that schema decision to ship user management. Verified the new routes 401 without auth against the live deploy; the 403-for-non-admin branch (`requireAdmin`, pre-existing/unmodified) wasn't separately exercised — no non-admin test account exists on this host.
7. **Hover-to-preview screenshot of instance** — **Implemented (2026-07-28).** Mechanism: dockur/windows' base image (`qemux/qemu`, not vendored in `windows/`) always starts QEMU with an HMP monitor on a unix socket at `$QEMU_DIR/monitor.sock` (`/run/shm` by default — confirmed by pulling `dockurr/windows` and reading its `/run/config.sh` + `/run/reset.sh` directly, since this isn't documented in `windows/docs`). `docker/template.ts`'s `captureInstanceScreenshot` runs two `docker exec`s into the instance's own container (no helper container needed, unlike `firewall.ts`'s pattern): one sends HMP's `screendump` command over the monitor socket via the image's own `openbsd-nc` and polls the resulting PPM file for two consecutive equal size reads (not just non-empty — a full 1920x1080 dump is several MB and a naive "-s file" check races a partial write); the other runs a pure-stdlib `python3 -c` (zlib only — the image ships no PIL/ImageMagick/netpbm) that re-encodes the PPM to PNG, with a length check against the declared width×height so a still-truncated read fails loudly (nonzero exit / no PNG magic) rather than emitting a structurally corrupt image. The PPM is deleted from tmpfs after conversion (best-effort). `GET /api/instances/:id/screenshot` (409 if not running, 502 on capture failure — same shape as `/stats`) serves the PNG directly; Dashboard.tsx shows it in a floating preview on a 350ms hover-intent delay over an instance's name (only for `running && phase === 'ready'` — nothing to capture pre-boot), refreshing every 4s while hovered. **Verified empirically without a live QEMU**: pulled the real `dockurr/windows` image and ran the exact trigger/convert commands against (a) a synthetic 1920x1080 PPM directly, and (b) a stub `AF_UNIX` monitor-socket listener that writes a real 6MB PPM in slow 300KB chunks (simulating an in-progress screendump) while driving the *actual* Node/dockerode `exec`+`demuxStream` code path from `template.ts` against a live container — the stability-poll correctly waited out the slow write, and the resulting PNG had valid magic bytes and correct dimensions end-to-end. Not verified: capture against a real booted Windows guest's actual QEMU monitor (this dev environment has no `/dev/kvm`-capable engine reachable from here) — the stub proves the mechanism and the race-condition fix, not real screendump content or its true write-latency profile.
8. **Client↔sandbox clipboard copy/paste** — **Corrected and implemented (2026-07-28).** The earlier "Already done" entry here was wrong: `allow="clipboard-read; clipboard-write"` on the iframe grants a browser permission, but does nothing by itself, and dockur/windows' own `windows/readme.md` says outright the web viewer "does not support ... clipboard sharing." Confirmed by pulling the image and reading `/usr/share/novnc/app/ui.js` directly: real noVNC (not KasmVNC), whose only clipboard feature is a manual panel (`clipboardSend`/`clipboardReceive` — open a sidebar textarea, paste text in to send it to the guest, guest-copied text lands in the same textarea for you to copy out yourself). No automatic OS-clipboard sync existed. Built real two-way sync instead: `webui/web/public/clipboard-sync.js` (new static asset, served at `/clipboard-sync.js`) dynamically imports the SAME `UI` module singleton the page's own inline script uses (`import(location.pathname.replace(/[^/]*$/, '') + 'app/ui.js')` — resolves to the identical absolute URL as vnc.html's own `import UI from "./app/ui.js"`, so the module cache hands back the same object, confirmed by reading vnc.html directly rather than assumed), then wires `UI.rfb`'s `clipboard` event to `navigator.clipboard.writeText` (guest copy → browser clipboard) and a `window focus` handler to `rfb.clipboardPasteFrom(navigator.clipboard.readText())` (browser copy → guest). `webui/src/proxy/viewer.ts`'s http-proxy now sets `replyOptions.onResponse`, which hands this app the raw upstream response for every proxied request (confirmed by reading `@fastify/reply-from`'s source: providing `onResponse` replaces its default `reply.send(res.stream)` entirely, so every non-HTML asset must still take that exact fallback path) — only `text/html` responses are buffered and get the script tag injected before `</body>`, with `Content-Length` recomputed against the modified byte length (the pre-injection header is already copied onto the reply by the time `onResponse` fires — leaving it stale would truncate the response in the browser). Verified the exact injection logic against the real `vnc.html` pulled from the image (correct byte delta, single injection point, valid surrounding context). Not verified: `navigator.clipboard.readText()` on window focus is well-known to be browser/permission-state dependent without a live user gesture — this can silently no-op on some browsers, and the real end-to-end behavior (both directions, in an actual browser, against a live QEMU monitor) has not been exercised — no `/dev/kvm` in this dev environment.
9. **Browser file upload into the OS** — **Implemented (2026-07-28).** Resolved the decision as scoped upload/download via dockur/windows' own built-in shared-folder feature, not a host filesystem path: `docker/template.ts` now sets `SAMBA=Y` (previously `N`) and binds a new per-instance volume (`sharedVolumeNameFor`, `sbx-<id>-shared`) at `/shared` — surfaced in the guest as a desktop shortcut + drive `Z:`, same lifecycle as the main disk volume (removed together on permanent delete, kept together on "retain disk"). `docker/files.ts` reads/writes that volume through a short-lived helper container (reuses `sandbox-firewall-helper:latest` — already a required deploy-time build for `firewall.ts`, so this added zero new deploy steps — with its `iptables` entrypoint overridden to `sleep` since `docker exec` needs a running container, unlike the archive-style approach originally considered) via the same exec-based approach `docker/template.ts`'s screenshot feature (#7) established, extracted into a shared `docker/exec.ts`. Filenames reach the shell as a positional arg (`sh -c '...' sh "$filename"`), never interpolated into script text, which rules out shell injection but NOT path traversal (`../etc/passwd` through a quoted arg still escapes `/shared` at the OS level, confirmed empirically) — `docker/validators.ts`'s new `sharedFileNameSchema` rejects `/`, `\`, and `..` before any of this runs. Fixed-cap limits (200MB/file, 2GB total per instance's shared folder) since there's no per-tier knob for this yet (#14's `resource_tiers` table doesn't cover it). New routes in `api/files.ts` (list/upload via `@fastify/multipart`/download/delete), all owner-scoped and deliberately NOT gated on the instance running — the volume exists independently of the container. UI: a new "Shared files" panel on `InstanceDetail.tsx`. **Found and fixed a real bug while building this**: `exec.inspect()` read immediately after a hijacked exec stream's `'end'` event can report a stale `Running: true`/null `ExitCode` for an exec that already finished successfully (confirmed empirically — a write-then-read pair intermittently saw this on a write that had, in fact, already persisted correctly) — `docker/exec.ts` now polls `inspect()` until `Running: false` before trusting `ExitCode`, a fix that also applies retroactively to #7's screenshot capture. Also found empirically: attaching stdin to an exec that has nothing to send and immediately `.end()`-ing it is unreliable (intermittently truncates the read to 0 bytes) where never attaching stdin at all is 100% reliable — `docker/exec.ts` only attaches stdin when there's real input to write. **Verified end-to-end**: ran the actual compiled module against a real Docker volume + helper container — list/upload/download/delete all round-tripped correctly, including a filename with spaces, parentheses, and a unicode em-dash, and a traversal/not-found case correctly threw rather than silently succeeding. Not verified: the real HTTP multipart route (`api/files.ts`) end-to-end through a browser, and the feature against an actual running Windows guest (no `/dev/kvm` here) — only the underlying `docker/files.ts` module and its exec mechanics were exercised directly. **Existing instances need recreation**: the `/shared` bind and `SAMBA=Y` are set at container-create time only (same situation as the earlier `/dev/net/tun` networking fix) — an instance created before this change has no `/shared` mount at all. `docker/files.ts`'s helper container would still mount `sbx-<id>-shared` (Docker silently auto-creates a missing named volume rather than erroring), so listing/upload/delete against an old instance would all report success while nothing ever reaches that instance's actual guest. New instances get this automatically; existing ones don't until recreated.

22. **Snapshot and clone support**: each instance's disk is a single Docker volume (`Binds: [\`${volumeName}:/storage\`]`, `docker/template.ts`), so the mechanism depends on what's actually on disk — a QEMU-level snapshot (qcow2 internal snapshot / monitor-socket `savevm`, if dockur/windows' `DISK_OPTIONS`/`STORAGE` format supports it) would be fast and let a running instance roll back in place; a Docker-volume-copy clone (new volume + `docker cp`/tar of the source volume's contents) is format-agnostic but only works stopped and is as slow as the disk is large. 23. **Per-instance network ingress/egress toggle in the web UI** — **Implemented (2026-07-28).** "ingress" is already zero today by design — no published ports, no inbound path except the webui's own proxy (see #18's "viewer is the only path in" invariant) — so there's nothing to toggle there; this shipped as an **egress on/off switch**. `sandbox_instances.egress_blocked` (migration `0002_workable_exodus.sql`) is the source of truth; `docker/firewall.ts`'s `ensureInstanceFirewall(networkId, { blockEgress })` ensures-or-removes a deny-all `DOCKER-USER` rule (same-bridge-scoped like the baseline RFC1918 rules, so the webui↔sandbox viewer path survives a block) based on the flag, and `removeInstanceFirewall` now unconditionally removes that rule too so orphan-network/teardown cleanup can't leak it. `POST /api/instances/:id/egress` persists the flag and applies it immediately if the instance's network already exists (otherwise the reconciler's per-sweep `ensureFirewallRules`, which now maps each `sbx-*-net` back to its instance row, converges it within one sweep — same self-healing pattern as the baseline rules). UI control lives in InstanceDetail's Access panel next to the existing "viewer is the only path in" copy. Distinct from #16 (admin-set default policy per tier) — this is a live, per-instance override a user triggers themselves.
24. **Graphical firewall/router builder + saved profiles** — **Implemented (2026-07-28).** A reusable, owner-scoped, per-instance-assignable egress policy on top of #16's inline open/blocked/allowlist modes, editable as a node graph rather than a CIDR textarea. New `firewall_profiles` table (`db/schema.ts`): `name`, `default_action` ('allow'/'deny' — what unmatched traffic does), an ordered `rules` JSON array (each `{id, action, protocol, cidr, portFrom?, portTo?, label?}` — array order IS iptables evaluation order), and a purely cosmetic `node_layout` JSON blob (never read by anything that enforces policy). `sandbox_instances` gets a nullable `firewall_profile_id` FK plus a new `egressMode` value, `'profile'`, that delegates to it instead of `egress_allowlist`. `docker/firewall.ts`'s `EgressPolicy`/`populateChain` gained a `'profile'` branch (`FirewallRule`, `compileProfilePolicy`) rather than a parallel enforcement path — it's appended in the exact same place allowlist mode's ACCEPT rules are, so the existing baseline-drops-first ordering guarantee (RFC1918/link-local DROPs always precede any policy-specific rule) applies to profile rules too: a rule "allowing" 192.168.0.0/16 structurally cannot match, since the earlier baseline DROP wins first (iptables is first-match). DNS is unconditionally accepted in this branch, same as allowlist mode, so a default-deny profile with no explicit DNS rule doesn't break name resolution. CRUD lives in new `api/firewallProfiles.ts`, owner-scoped throughout (no cross-user IDOR on assignment); editing a profile reapplies immediately to every instance currently assigned it (same "apply now, reconciler self-heals otherwise" pattern as #16); deletion is refused (409) while any *live* instance still references it, and any lingering reference from a *soft-deleted* instance is nulled out first since `db/client.ts` runs with `PRAGMA foreign_keys = ON`. `reconciler/index.ts`'s `ensureFirewallRules` resolves `firewall_profile_id` → compiled policy every sweep (batched lookup, not one query per instance) and **fails closed to `blocked`** if an instance references a profile that no longer exists, rather than silently falling open. UI: new `pages/FirewallProfiles.tsx` (list/create/delete) and `pages/FirewallProfileEditor.tsx` + `components/FirewallGraphEditor.tsx` (new `reactflow` dependency — the one new frontend dependency this added), rendering a deliberate **star topology only**: a fixed "This Sandbox" source node fans out to each rule plus a fixed "everything else" default endpoint; there is no destination-to-destination or instance-to-instance edge, because the guest has no L2 presence on its bridge (`NETWORK=user`/passt) — anything richer than a star isn't enforceable by the underlying per-instance iptables chain. Dragging a rule node vertically re-derives that rule's position in the array (and therefore its iptables evaluation order) from top-to-bottom position; `InstanceDetail.tsx`'s existing Access panel gained a fourth mode ("Profile — use a saved firewall profile") with a profile picker, reusing the same single write path (`POST /api/instances/:id/egress`, now a Zod discriminated union) rather than a competing route. Domain/hostname-based rules are explicitly out of scope — iptables is IP-based and there's no DNS-resolution/refresh machinery in this project to back a "allow github.com" rule; the UI only ever accepts CIDR/port. **Not verified at runtime**: the `'profile'` branch of `populateChain` has never executed against a real host (no Docker socket / `/dev/kvm` in this environment, same limitation #16 shipped under), and the graph editor has never rendered in a browser — `tsc`/`vite build` passing confirms the types line up, not that dragging, saving, or the compiled iptables rules behave as intended. Verify both empirically before relying on this in production.
25. **Enterprise/NGFW feature backlog (candidate list, not started)** — user supplied a wishlist of software-firewall capabilities to evaluate against this project. Grouped by actual fit for a single-host Docker/iptables egress controller in front of QEMU-in-Docker sandboxes (not a dedicated network appliance), so priority is real rather than just alphabetical:
    - **Directly buildable on today's architecture, moderate lift each**: stateful packet inspection (already implicit — return traffic rides Docker's own bridge conntrack ESTABLISHED/RELATED accept, same mechanism #1's "general internet open" default already depends on; making it *visible/explicit* rather than incidental is the actual task); IPv6 filtering (validators.ts is IPv4-only by deliberate choice today — extend only if a bridge ever goes dual-stack); anti-spoofing/SYN-flood protection (kernel `rp_filter` + `iptables -m limit --syn`, per-chain); basic rate limiting/QoS (`iptables -m hashlimit` or `tc` per bridge); policy dry-run + automatic rule-conflict detection (a client-side pass flagging a rule shadowed by an earlier broader one in #24's rule list — already flagged separately as a gap in #24's own review, no new infra needed).
    - **1:1/destination NAT is a decision, not a build**: source NAT (outbound masquerade) already happens via Docker bridge networking. Destination/1:1 NAT would mean port-forwarding traffic *into* a sandbox — directly reverses the standing "the viewer is the only path in" invariant (#9/#18). Needs the same explicit call #18 needs before any implementation.
    - **Real projects, each its own design pass**: dynamic GeoIP filtering (MaxMind/GeoIP feed + ipset — recurring data-feed maintenance, not just code); DNS security/sinkholing/DoH-DoT inspection, NetFlow/IPFIX/sFlow/SIEM export, and real-time traffic telemetry all sit squarely behind #17's still-unresolved network-capture-tier decision (passt has no host-visible tap — none of these can be built before #17 is resolved, and shouldn't be estimated until it is); site-to-site/client-to-site VPN (WireGuard/IPsec/SSL) is an orthogonal subsystem (a VPN sidecar/gateway), not an extension of egress policy; API-first/Terraform-Ansible IaC is reasonable given the REST API already exists, but needs a stability/versioning commitment first; identity-aware firewalling (AD/LDAP/OAuth2/SAML) is really an auth-system project — today's auth is local email/password only (`auth/session.ts`), with no directory integration to hang per-identity rules off of.
    - **Wrong layer for this project, not just unstarted**: DPI, TLS/SSL decryption + inspection, URL/domain filtering, DLP, IDS/IPS, inline AV/malware scanning, behavioral anomaly detection, and threat-intel (STIX/TAXII) feed integration all require an inline traffic-inspection engine (e.g. Suricata/Snort, a TLS-terminating proxy with its own CA) sitting in the actual packet path — which today is passt/usermode networking with no visible tap at all (the same #17 blocker, one layer more fundamental: these need packets in hand before they can even start, and #17 is about getting packets visible, not inspecting them). Application control/protocol recognition needs the same DPI foundation. None of this is "not built yet" so much as "this app is a sandbox-lifecycle manager with an egress-policy feature, not a network appliance" — treat as a candidate for a separate bolt-on service against a resolved #17 tap, not a `docker/firewall.ts` feature.
    - **Explicitly out of scope barring a real, measured need**: eBPF/DPDK data-plane rewrite, multi-core scaling/RSS, hardware offload (SmartNIC/AES-NI), and HA active/active with state sync are line-rate network-appliance concerns for multi-Gbps hardware. This runs iptables on one Docker host for a handful of sandbox VMs — there is no throughput problem today that any of these would solve, and building them means leaving the "sandbox manager with an egress feature" architecture entirely for a dedicated data-plane rewrite. Microsegmentation and ZTNA enforcement are, in effect, already this project's model at the VM level (one bridge + one iptables chain per sandbox instance, no lateral traffic by default) — process/container-level segmentation *inside* the guest isn't reachable, since nothing in-guest is instrumented today.
